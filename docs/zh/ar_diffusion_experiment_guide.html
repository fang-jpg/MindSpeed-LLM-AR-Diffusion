1. 先把原理讲明白

Block size：B

模型每次准备并行生成多少个 token。比如 B=16，就是一次处理 16 个待生成位置。

解码步数：S

模型用多少次前向计算把这个 block 填完。S 越少，每次要同时确定的 token 越多。

加速比

Diffusion 的真实 decode tok/s 除以同一 checkpoint 的 AR decode tok/s。

模型性能

先用 GSM8K 比较 12 个配置，再把三个代表配置放到五个任务上完整评测。

一个 block 有 B 个 token，用 S 步填完；粗略并行能力约为 B / S

例如 B=16、S=4，平均每一步要确定 4 个 token。它通常比 S=16 更快，但也更容易出错。

这轮只保留一条主线：改变 B 和 S，然后同时测 Speedup 与 GSM8K。没有阈值 sweep、SOL、checkpoint 轨迹或训练遗忘分析。

每组记录 Diffusion tok/s、Speedup、GSM8K 和显存。

选最快点、性能最好点、速度性能平衡点。

只对三个点测 MMLU、GSM8K、HumanEval、BoolQ、BBH。

所有实验必须固定

  • 同一个 joint checkpoint、tokenizer 和 prompt。
  • temperature=0。
  • 速度测试时 AR 和 Diffusion 都固定生成 128 token，都忽略 EOS。
  • warmup 5 次，正式重复 20 次，NPU 同步后计时。
  • GSM8K 性能测试允许正常遇 EOS，生成上限使用 512 token，不使用速度测试的 128-token 限制。
  • GSM8K 固定使用仓库默认 direct 模式和同一份 3-shot prompt；若改用 CoT，所有 AR/Diffusion 配置必须一起改，不能混用。
  • 性能测试时使用同一批样本、相同答案解析和 seed=42。
指标口径已统一：AR 基准、12 组主实验、选点规则和两张主图都使用 GSM8K；MMLU 只在最后三个候选的五任务完整评测中出现。

3.1 generation.py 的核心修改

def block_diff_generate(
    model,
    prompt_ids,
    max_new_tokens,
    block_length,
    steps_per_block,       # 新增：不再等于 block_length
    ...
):
    remaining = max_new_tokens
    while remaining > 0:
        cur_block_length = min(block_length, remaining)
        # 为当前 block 建 MASK
        # 恰好执行 steps_per_block 次去噪
        # 每一步提交一部分 token
        remaining -= cur_block_length

论文式主实验建议 block 初始全部为 MASK。当前代码会给每个 block 放一个 AR seed；为了直接对照论文，主实验中应关闭这一步，不再额外做 seed 消融。

3.2 每次运行只需输出这些数字

{
  "block_size": 16,
  "steps_per_block": 4,
  "generated_tokens": 128,
  "forward_calls": 40,
  "decode_time_ms": 1234.5,
  "decode_tokens_per_second": 103.7,
  "speedup_vs_ar": 2.15,
  "peak_memory_gb": 21.3,
  "gsm8k_accuracy": 63.4
}

forward_calls 要记录真实次数，包括去噪和每个 block 的 KV refresh；加速比最终只使用实测 tok/s。

4.6 推荐执行顺序

  1. 先确认 step 102500 的模型目录、GSM8K 数据和 100 条测速 prompt。
  2. 跑 AR-BASE 的速度与 GSM8K，得到所有比较的分母和性能基准。
  3. 按 B=4、8、16、32 的顺序跑 12 组速度。
  4. 再按相同顺序跑 12 组 GSM8K。
  5. 把数字填入 Markdown 主表。
  6. 选三个代表配置，再做五任务；不要一开始就跑所有任务。

5. 关于 embedding 拷贝到 lm_head

结论：初始化 Base 模型时可以是对的；加载训练后的 joint checkpoint 时，不一定对。

当前模型里的 lm_head 是一个独立参数，训练中会更新。现在的 from_pretrained 流程是：

  1. 先从 checkpoint 加载 lm_head.weight。
  2. 加载完成后，无条件用 embed_tokens.weight 覆盖它。

如果加载的是原始 Base，或者 checkpoint 根本没有 head，这个复制可以用来初始化。但如果加载的是已经训练好的 joint checkpoint，head 已经学过 diffusion/AR 目标，再覆盖就会丢掉训练后的 head。

最简单的判断：检查 joint checkpoint 是否包含 lm_head.weight。若包含，就应该保留；只有缺失时才从 embedding 复制。
if "lm_head.weight" in loading_info["missing_keys"]:
    model.lm_head.weight.copy_(model.model.embed_tokens.weight)

如果你的设计要求 embedding 和 head 永远相同，则应该在训练阶段真正共享同一个 Parameter，而不是只在加载后复制一次。这个确认不作为实验，不会放进 12 组主表。

6. 什么时候才需要重新训练不同 block

第一轮先用现有 B_train=8 checkpoint 完成 12 组解码实验。这回答的是“推理时 B 和 S 如何影响速度与性能”。

如果 mentor 进一步问“训练时 block size 是否影响最终模型”，再从同一个 AR checkpoint 训练 B_train=4/8/16/32 四个模型。四个 run 只能改变 block size，其他训练条件保持一致。

7. 最后怎么向 mentor 讲

  1. 先讲设置：我们测试 B=4/8/16/32，每个 B 测快速、平衡、保守三档 S。
  2. 再讲速度：哪个配置真实 Speedup 最高，不用理论值代替实测值。
  3. 再讲性能：减少 S 或增大 B 后，GSM8K 和五任务平均下降多少。
  4. 最后给推荐：最快配置、性能最好配置、推荐平衡配置各一个。

只画两张图：

  • Speedup - GSM8K 散点图：越靠右越快，越靠上性能越好。
  • S - 性能/速度曲线：展示增加解码步数如何恢复性能、牺牲速度。
推荐点定义：在五任务平均下降不超过 1 个百分点的配置中，选择 Speedup 最大的配置。

8. 与论文的关系

论文比较了 block length 4、8、16、32，并显示 block 变大后可接受长度增加，但平均任务性能不是单调上升。我们的 12 组实验就是用当前 1.7B checkpoint 检查同样的速度—性能趋势。

论文的 learned SOL sampler 需要额外训练；当前仓库没有对应 sampler，所以本轮不做 SOL，只研究最容易解释的 B 和 S。
